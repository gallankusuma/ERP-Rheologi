P0 — MRP → PR lineage sekarang bisa menunjuk MPS yang salah. Standalone MRP memang mengagregasi kebutuhan dari semua Confirmed MPS dalam satu tahun. Tetapi saat generate PR, revisi baru mencari semua Confirmed MPS tahun tersebut lalu mengambil header pertama sebagai mps_header_id. Kalau 2026 punya MPS Januari, Februari, Maret, dst., satu PR yang merupakan gabungan beberapa MPS bisa malah dicap seolah berasal dari satu MPS saja. Ini false provenance dan menurut gue lebih bahaya daripada field kosong. Jangan pilih arbitrary first MPS. PR Item perlu lineage many-to-many ke MPS detail yang benar-benar berkontribusi terhadap material requirement.
P1 — Backend Forecast Trace sudah benar, tapi UI Production Planning belum menampilkannya. Backend sekarang sudah return forecast_number, period, week, year, quantity. Tapi modal Production Planning masih menampilkan semua source selain SO/Project cuma sebagai tulisan “Forecast”; src.ref, period, dan week yang baru tidak digunakan. Jadi operator masih belum bisa melihat: Forecast FC-xxxx → W33 → 5,000.
P1 — Week MPS di halaman Work Orders masih mismatch field. UI memakai wo.mps_week_number, sedangkan API /workorders mengembalikan w.\*, yang field relational-nya adalah week_number; tidak ada alias mps_week_number. Jadi WO bisa punya MPS Number tetapi Minggu MPS-nya tetap kosong. Production Planning sudah benar menggunakan alias wo_week_number; Work Orders belum.
P1 — Summary badge tidak mengikuti filter bulan. List /workorders sekarang memang sudah menggunakan month/year filter — temuan ini closed. Tetapi frontend tetap mengambil /workorders/summary tanpa month/year, sementara summary backend menghitung seluruh tabel work_orders. Jadi kalau pilih Agustus, tabel mungkin menunjukkan 8 WO tetapi badge status bisa menunjukkan total seluruh history. Buat user ini tetap memberi kesan “WO kok banyak banget”. Summary harus menggunakan filter periode yang sama atau dihitung dari result list aktif.

Yang lainnya gue accept: month/year filtering sudah real di backend, /summary sudah dipindahkan sebelum /:id, endpoint PATCH /:id/status sekarang ada, dan manual WO sudah punya dedicated source_reason plus migration dari notes.

Jadi verdict gue:

3d6823e = WO PROVENANCE substantially improved, tetapi belum FIRM karena masih ada 1 P0 false-lineage + 3 P1 presentation/filter mismatches.

Untuk development gue akan fokuskan cuma ini: jangan tambah fitur baru dulu. Fix MRP→PR lineage supaya tidak pernah menebak satu MPS, lalu selaraskan Forecast trace, MPS week, dan summary filter di UI. Setelah itu kita test pakai WO yang nyata dan pilih satu WO secara random: dari layar harus bisa langsung dijawab “WO ini muncul karena demand apa, dari dokumen mana, MPS minggu berapa, dan siapa yang membuatnya.”
